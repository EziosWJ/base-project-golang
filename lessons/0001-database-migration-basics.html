第一课：为什么 Go 后端需要 Migration

目标不是学一个工具名，而是确保 Java→Go 迁移后，每个环境的 PostgreSQL 都拥有同一份、可追溯的表结构。

先分清两件事

数据库 Schema 是当前状态：例如是否存在 sys_user 表、它有哪些字段和索引。
Migration 是改变状态的一步：例如“创建 sys_user 表”或“给它添加 email 列”。
Git 中的 migration 001：创建用户表↓ migration 002：创建角色表↓ migration 003：创建 auth_session 表

为什么不能只靠手工建表？

因为开发、测试、生产会逐渐不同步：你在本机加过字段，不代表部署服务器也加过。Migration 将每次变更写进 Git；部署时工具检查哪些步骤尚未执行，再按顺序补齐。Goose 会在数据库中保存已执行版本记录。

它与 GORM AutoMigrate 有何区别？

AutoMigrate 根据当前 Go struct 推测表结构并尝试修改。它适合本地试验，但难以表达、审查和追踪每一次生产 Schema 变更。项目选择 Goose，是让 SQL 变更成为可审查、可复现的代码版本。

放进本项目，就是这样

第一批 migration 创建 PostgreSQL 中迁移认证所需的表和内置数据。日后新增字段时，新增一份 migration；不要回头改已经在环境中执行过的旧文件。Java 的 MySQL SQL 只是行为参考，Go 的 PostgreSQL migration 是新的权威结构来源。
